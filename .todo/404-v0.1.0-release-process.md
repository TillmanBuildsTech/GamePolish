# 404 — The v0.1.0 release process

## Objective
A written, executable release process for `v0.1.0`: the tag convention, a `check-version` guard that fails before anything
builds, a draft-then-publish order, artifact filenames that stay stable across releases so the website's
`/releases/latest/download/...` links keep resolving, a `checksums.txt`, and a pre-tag checklist — enough that a second person
produces a draft release without asking a question.

## Context
`../game-polish-notes/docs/ci-release.md` describes the *finished* process: signed `.msix`/`.exe` on Windows, signed and
notarized `.dmg` on macOS. **None of that is this release** — signing and notarization are task **610** (phase 6, v1.0), real
installers (`.msix`, NSIS/WiX `.exe`, `.dmg`) are **611**, and the in-app auto-updater plus `update-manifest.json` is **605**.
Do not attempt any of them here.
v0.1.0 artifacts therefore carry **no signature**, and that consequence belongs in the release notes: Windows SmartScreen shows
"Windows protected your PC" → *More info* → *Run anyway*; macOS Gatekeeper refuses the quarantined build until a tester clears
it with `xattr -dr com.apple.quarantine <app>`. No secret from `ci-release.md` (`WINDOWS_CERT_*`, `APPLE_*`) may be referenced
by the v0.1.0 workflow.
403 provides the publish commands and 104 the CI workflow this extends; **405 blocks this task in practice** — its signed
acceptance record is a pre-tag input. Verified 2026-10-15: the repo has **no git remote** and the `game-polish` owner does not
exist (`gh api orgs/game-polish` → 404; `Tillman32` is in `MorphStack`, `M-Wolf-Media-Marketing`, `TillmanBuildsTech`), so
nothing can be tagged or linked until 402 settles it.

## Scope
- `RELEASING.md`: the checklist, in order, with the real commands.
- `.github/workflows/release.yml`: `check-version` → two publish jobs → `publish` creating a draft.
- `CHANGELOG.md` with a `0.1.0` section, plus the release-body text.
- The artifact-name decision (written once, never changed) and `checksums.txt` generation and upload.
- `ci-release.md` updated in the same commit to record the v0.1.0 reality, with no signing secret referenced anywhere — required
  by the definition of done for CI/release config.

## Out of scope
- Signing, notarization, certificates, every secret under "GitHub Secrets Required" (610).
- `.msix` / installer `.exe` / `.dmg` (611); `update-manifest.json` and the update banner (605).
- The website and its links (706) — this task only guarantees the filenames they depend on; prerelease/beta tags and
  `nightly.yml`. Never move or re-point a published tag.

## Implementation notes
**Tag convention** (`ci-release.md` "Version Tag Convention"): `v<major>.<minor>.<patch>` → `v0.1.0`, trigger
`'v[0-9]+.[0-9]+.[0-9]+'`. The tag carries the `v`, the csproj `<Version>` does not — pitfall 6 in `.todo/000-CONVENTIONS.md` —
and tags are expensive to move, so the guard runs first. Verified here: `dotnet msbuild <csproj> -getProperty:Version -nologo`
prints the bare `0.1.0` (MSBuild 17.8+; the pinned SDK 10.0.401 has it).
**`check-version`** — the first job; every other job `needs:` it:
```yaml
check-version:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-dotnet@v4
      with: { global-json-file: global.json }
    - name: Tag must match csproj <Version>
      run: |
        TAG="${GITHUB_REF_NAME#v}"; PROJ=$(dotnet msbuild GamePolish.Desktop/GamePolish.Desktop.csproj -getProperty:Version -nologo | tr -d '\r')
        [ "$TAG" = "$PROJ" ] || { echo "::error::tag $GITHUB_REF_NAME != Version $PROJ"; exit 1; }
```
**Build jobs** run 403's commands verbatim (`--self-contained true`) and upload each publish directory with
`actions/upload-artifact`; `publish` downloads both and creates the release.
**Artifact names — a contradiction to resolve.** `ci-release.md` gives versioned names (`GamePolish_1.2.0_x64.msix`) but the
website section links to **unversioned** ones (`GamePolish_x64-setup.exe`). Both cannot describe one file, and the note insists
filenames "stay consistent across releases for these links to remain stable": GitHub matches that path exactly, so a
versioned-only artifact breaks the link at the next release. Ship both:
```
GamePolish_0.1.0_x64.zip      GamePolish_x64.zip        # versioned + the stable alias the website links to
GamePolish_0.1.0_aarch64.zip  GamePolish_aarch64.zip    # versioned + stable alias
checksums.txt                                           # cd artifacts && sha256sum *.zip > checksums.txt
```
No installer exists at v0.1.0, so the alias is a `.zip`; when 611 lands, `GamePolish_x64-setup.exe` and `GamePolish_aarch64.dmg`
take over as the stable names. Decide once, in `ci-release.md`, and flag the contradiction for the human. Keep the note's `x64`
/ `aarch64` tokens (the RIDs stay `win-x64` / `osx-arm64`). `/releases/latest/download/<file>` resolves only to the newest
non-draft, non-prerelease release, so those links are dead while this release is a draft.
**Draft, then publish.** Fill the assets in from the build jobs' artifacts:
```bash
gh release create v0.1.0 --draft --title "Game Polish v0.1.0" --notes-file CHANGELOG_LATEST.md \
  GamePolish_0.1.0_x64.zip GamePolish_x64.zip GamePolish_0.1.0_aarch64.zip GamePolish_aarch64.zip checksums.txt
gh release edit v0.1.0 --draft=false --latest    # only after a human reviews the draft
```
**Pre-tag checklist** — green with pasted output, before `git tag`:
1. `git status --short` clean on `main`; `dotnet build -c Release` with 0 warnings, 0 errors.
2. `dotnet test` — paste the real pass/fail counts; `dotnet format --verify-no-changes` passes (103's gate).
3. The 405 acceptance record is signed off with no `NOT RUN` rows.
4. `<Version>` equals the tag without the leading `v`.
5. `CHANGELOG.md` has a `0.1.0` section naming the SmartScreen / Gatekeeper consequence.
6. `ci-release.md` updated in the same commit; no signing secret in the workflow.
If the guard fails *after* the tag is pushed: delete the draft, fix `<Version>`, cut `v0.1.1`. Never force-push `main`, never
retag.

## Acceptance criteria
- `RELEASING.md` exists, and a person who did not write it can follow it to a draft release without asking a question — that
  handoff is the test.
- The `check-version` job fails on a deliberately mismatched tag and passes on the matching one; both runs pasted.
- Following the checklist produces a **draft** release with the five expected filenames, whose checksums match a locally
  recomputed `sha256sum`, and `ci-release.md` records the v0.1.0 reality in the same commit.
- The report names the deferred parts (610 / 611 / 605) and the Gatekeeper / SmartScreen consequence of shipping unsigned.
