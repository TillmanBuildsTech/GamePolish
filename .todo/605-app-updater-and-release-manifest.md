# 605 — App auto-updater and release manifest

## Objective

The publisher emits an `update-manifest.json` for every release, and the desktop app checks it at
launch, shows a non-blocking "Update available" banner with Install & Restart / Later, verifies the
download's SHA-256 before applying, and applies the update by the platform-appropriate mechanism.

## Context

Authoritative: `../game-polish-notes/docs/ci-release.md` (In-App Auto-Updater, Build Matrix, the
`publish` job, Branch & Tag Strategy). **This task extends `403` (packaging) and `404` (the tag/release
workflow):** `404` produced the tag-triggered release; this adds the manifest the client consumes and
the client itself.

**One honesty note about the check URL.** ci-release.md says the app checks
`gamepolish.app/releases/latest` on launch, but that service endpoint does not exist until phase 7
(`701`). For v1.0 the client must therefore fetch the manifest from the GitHub release directly —
`https://github.com/game-polish/game-polish/releases/latest/download/update-manifest.json` — and the
service URL becomes a phase-7 swap. Do not hard-code a host that returns nothing at v1.0.

## Scope

- **Manifest contract** (generated by the `publish` job, exactly the ci-release.md shape):

  ```json
  {
    "version": "1.2.0",
    "notes": "Bug fixes and performance improvements.",
    "pub_date": "2026-10-15T21:00:00Z",
    "platforms": {
      "windows-x64": { "url": "…/GamePolish_1.2.0_x64-setup.exe", "sha256": "<checksum>" },
      "osx-arm64":   { "url": "…/GamePolish_1.2.0_aarch64.app.tar.gz", "sha256": "<checksum>" }
    }
  }
  ```
- In-app check at launch (gated by the App Settings "Check for app updates" preference: Automatically /
  Never) plus a manual "Check for updates" trigger from the About/App Settings footer.
- Non-blocking banner: `Update available — v1.2.0 is ready. [Install & Restart] [Later]`.
- SHA-256 verification of the downloaded artifact against the manifest before anything is applied.
- Per-platform apply: Windows (MSIX / `.exe`) and macOS (`.dmg` / `.app.tar.gz`), with each one's real
  capabilities and limits stated, not glossed.
- Prerelease handling: tags matching `v*.*.*-*` are published with `--prerelease` and are invisible to
  `/releases/latest`, so the client never accidentally offers them.
- A beta channel decision.

## Out of scope

- Signing and notarization of the artifacts (`610`) — the updater consumes them.
- Installer construction (`611`).
- Delta/incremental updates; the manifest carries whole artifacts.
- The `gamepolish.app` service (`701`); the URL swap is noted above and deferred.

## Implementation notes

- **Manifest check.** `GET` the `update-manifest.json` URL, parse `version` and `pub_date`, and compare
  `version` to the running build's version with a semantic-version comparer. A fetch failure is silent
  (no internet, no release yet) and never blocks startup — the check runs on a background task.
- **Prerelease rule.** The manifest is uploaded by the same `publish` job. A prerelease tag
  (`v1.0.1-beta`) is created with `gh release create --prerelease`, so GitHub's `/releases/latest`
  redirect — and therefore the `/releases/latest/download/update-manifest.json` URL — keeps resolving to
  the last stable release and never to a beta. The client relies on that and needs no prerelease-suffix
  parsing for the stable path. **Beta channel decision: off for v1.0.** There is no opt-in; add one only
  when there is a prerelease population that wants it. Record the decision in the App Settings copy so
  users are not surprised.
- **Checksum.** Download to a temp file, compute SHA-256 streaming, compare (case-insensitive) to
  `platforms.<rid>.sha256`. On mismatch: delete the temp file, show an error, and do **not** run the
  installer. A mismatch is a tampering or truncation signal and is fatal for that attempt only.
- **Windows apply.** Two cases, stated honestly:
  - *MSIX-installed*: an MSIX can be updated in place only by a package with the **same identity and
    package family name, signed by the same publisher**, at a higher version. A self-update therefore
    requires the new `.msix` present locally and applied through the Package Deployment API; an unsigned
    or differently-signed package cannot self-update. Cross-publisher or unsigned builds must go through
    the `.exe` installer.
  - *`.exe`-installed* (WiX/NSIS, `611`): download `GamePolish_<v>_x64-setup.exe`, verify its hash,
    launch it (the user gets the normal installer/UAC prompt), and exit the current instance so files
    are not locked. There is no silent, elevation-free self-update for a per-machine install.
- **macOS apply.** Download the `.dmg`, verify the hash, then mount and swap: `hdiutil attach
  GamePolish_<v>_aarch64.dmg`, copy `GamePolish.app` over the installed copy in `/Applications` (or the
  user's chosen location), `hdiutil detach`, relaunch. The replacement must carry a valid Developer ID
  signature or Gatekeeper re-prompts. The `.app.tar.gz` variant exists for a Sparkle-style bundle swap
  and is the artifact the manifest points at for `osx-arm64`.
- **Consent.** "Install & Restart" is a user action, never automatic. "Later" dismisses for the session
  (re-offer next launch unless the version is now ignored); store "skip this version" only if the UI
  offers it.
- The banner is a toast/drawer item (`307`), not a modal; it must not block the Library.
- Compare versions from a single source: the assembly version baked from `<Version>` in
  `GamePolish.Desktop.csproj`. The manifest `version` must equal the tag — `404`'s `check-version` job
  already enforces tag == csproj, so the manifest inherits that guarantee.

## Acceptance criteria

- The `publish` job writes `update-manifest.json` with `version`, `notes`, `pub_date` and both `platforms`
  entries (`windows-x64`, `osx-arm64`), each with `url` and `sha256`, and uploads it with the artifacts.
- Given a fixture manifest and a fixture artifact, the client computes the artifact's SHA-256, accepts a
  match and rejects a tampered file (deleting the temp download).
- A newer version shows the banner with the exact text; "Later" dismisses and does not re-show in the
  session; the app keeps working with no modal.
- A version equal to or older than the running build produces no banner.
- A manifest whose `osx-arm64` URL is served to Windows is ignored (platform selection by RID).
- A prerelease tag produces a GitHub *prerelease*, and the `/releases/latest/download/update-manifest.json`
  URL still resolves to the last stable release (verified with `gh release view`).

## Verification

```bash
gh release list                                   # prereleases flagged, stable shows as 'Latest'
gh release view <stable-tag> --json assets -q '.assets[].name' | grep update-manifest.json
curl -sL https://github.com/game-polish/game-polish/releases/latest/download/update-manifest.json | jq .
dotnet test --filter FullyQualifiedName~Updater   # manifest parse, version compare, checksum
```

The apply step (running the installer, swapping the `.app`) cannot be exercised end to end on this
Windows host for macOS; the manifest/version/checksum logic is unit-tested, the Windows `.exe` apply is
observable locally, and the macOS apply is proven by a real Mac or a CI smoke job that mounts the `.dmg`.
